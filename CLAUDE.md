## Project

A web Freecell card game built with Next.js 15 (App Router), React 19, Phaser 3, and PostgreSQL. Users get one deterministic "daily deal" per day (like Wordle), can complete it, and track streaks/stats. Deployed on Vercel with Neon Postgres in production.

## Commands

```bash
npm run dev        # start Next.js dev server (localhost:3000)
npm run build      # production build (also surfaces type errors)
npm run lint        # eslint
npm run lint:fix    # eslint --fix; run before pushing
```

There is no test framework configured in this repo (no jest/vitest, no `*.test.*` files, no `test` script). Do not assume one exists.

### Local database

Local dev uses dockerized Postgres, not the Vercel/Neon flow:

```bash
docker compose build
docker compose up      # starts `db` (Postgres) and `adminer` (GUI at localhost:8080)
docker compose down
```

The `deals` table is seeded from a CSV in `db-init/` via `COPY` in `db-init/init.sql`, generated by `scripts/generate_shuffled_deals.py` (shuffles ~1M Freecell seeds, one per calendar day starting 2025-07-01, with a fixed RNG seed so the mapping is reproducible). DB init only runs on first volume creation — if the volume already exists, run `init.sql` manually via adminer. Production DB is Neon Postgres; do not run the commented-out `COPY` line from `init.sql` in Neon's SQL editor.

Required env vars: `.env.local` needs `GOOGLE_CLIENT_ID/SECRET`, `DISCORD_CLIENT_ID/SECRET`, `NEXT_AUTH_URL`, `AUTH_SECRET`, `DATABASE_URL`; `.env` needs `POSTGRES_PASSWORD` matching the password embedded in `DATABASE_URL`.

The `Dockerfile` and the `app` service in `docker-compose.yml` are intentionally dormant — the app itself deploys via Vercel, not a container; only kept as scaffolding.

## Architecture

### Two halves: React shell vs. Phaser game engine

React (`src/app`, `src/components`) owns everything *around* the game: auth, routing, overlays (login/stats/help), daily-deal fetching. Phaser (`src/phaser`) owns the game itself and runs independently once mounted — it does not receive props/state updates from React after boot.

- `src/components/game/PhasorGame.tsx` dynamically imports `@/phaser/main` in `useLayoutEffect` (Phaser must not be SSR'd/bundled server-side), calls `StartGame(containerId, seed)` with the seed from `useDailyDeal()` (`src/components/context/DealContext.tsx`, populated via SWR from `/api/deal/current`).
- The **only** channel back from Phaser to React is `src/phaser/EventBus.ts`, a shared `Phaser.Events.EventEmitter`. On win, `src/phaser/scenes/Game.ts` emits `"game-completed"`; `PhasorGame.tsx` listens and `POST`s to `/api/completion`.
- In-progress game state is *not* shared with React or the server at all — it lives only in `localStorage` (see Save system below). Only a finished game's summary gets sent to the backend.

### Phaser engine: domain/state/Controller/View pattern

`src/phaser` is organized into parallel modules — `card/`, `deck/`, `game/`, `move/`, `pile/`, `session/`, `meta/` — each generally following the same internal split:

- **`state/`** — plain serializable data types + pure factory functions (e.g. `card/state/Card.ts`).
- **`domain/`** — pure, side-effect-free functions that transform state and encode game rules (e.g. `game/domain/FreecellRules.ts`, `move/domain/CardMoveLogic.ts`, `card/domain/CardLogic.ts`). Always return new state, never mutate.
- **`*Controller.ts`** (module root, e.g. `CardController`, `PileController`, `SessionController`) — imperative glue: holds `model` (state) + `view`, mutates `model` via the pure domain functions, then calls `view.applyState(...)`.
- **`*View.ts`** — Phaser-specific rendering, kept separate from game logic.

When changing game rules, edit the `domain/` functions, not the Controllers or Views. When changing visuals/animation, that's `*View.ts` + `constants/`.

`src/phaser/scenes/Game.ts` is the orchestrator: builds `SaveController`, loads/validates `Meta` (daily seed + completion flag), creates `SessionController`, deals via `DeckController`, builds a `PileController` per pile, wires move history through a `PubSubStack<CardMoveSequence>` (push/pop/clear → animated execute/undo/redeal via an `AsyncQueue`), sets up input (`game/input/`), and runs a 1s timer for the session clock + autosave. `update()` checks `FreecellRules.areAllTableausOrdered` every frame; on win it locks input, auto-plays remaining cards, marks `Meta` complete, persists, and emits `"game-completed"`.

### Save system (`src/utils/save`)

A generic, Phaser-agnostic localStorage persistence framework, decoupled from any one module:

- `ISaveable<T>` — interface with `get()/set()` (bound accessors into the owning module's state) and `getSnapshot()/loadFromSnapshot()`.
- `SaveController.ts` — registry of `ISaveable`s; `saveToStorage()`/`loadFromStorage()`/`resetStorage()`.
- Each module opts in independently via a `*Saveable.ts` (`MetaSaveable`, `SessionSaveable`, `MoveSaveable`) registered in `Game.ts`. Storage key: `freecellwithfriends_save`.

This is entirely separate from the Postgres `games` table, which only stores completed-game history.

### Auth (`src/auth`)

NextAuth v4, JWT strategy, Google + Discord OAuth providers, no NextAuth DB adapter (Postgres writes are manual, in the `signIn` callback).

**Important:** `src/auth/ids.ts` derives user IDs as deterministic UUIDv5s from `provider:providerAccountId`, namespaced by a hardcoded UUID constant. Never change that namespace string — doing so silently reassigns every existing user's ID and orphans their save data/stats.

`config.ts`: `jwt` callback stamps `fwf_uuid` onto the token; `session` callback copies it to `session.user.id`; `signIn` calls `upsertNewUser` and redirects to `/?overlay=login&error=...` on failure.

### DB layer (`src/lib/db`)

Uses the `postgres` package directly (tagged-template SQL, no ORM). `src/lib/db.ts` exports a single `sql` client singleton from `DATABASE_URL`; all queries import it.

- `deals.ts`, `games.ts`, `streaks.ts`, `users.ts` — single-table reads.
- `transactions.ts` — multi-statement ops via `sql.begin`:
  - `upsertNewUser` — creates user + streak row.
  - `upsertGame` — idempotent; guarded with `WHERE games.completed = false` so a completed game can never be overwritten by a stale/late client sync.
  - `updateStreakOnCompletion` — continues the streak only if `last_deal_id === dealId - 1`; wraps the game upsert + streak update in one transaction.

Schema (`db-init/init.sql`): `users(id UUID PK, email)`, `deals(id, seed UNIQUE, date UNIQUE)`, `games(user_id, deal_id, elapsed_time_ms, moves JSONB, completed, PK(user_id, deal_id))`, `streaks(user_id PK, curr, max, last_deal_id)`.

### API routes (`src/app/api`)

Thin — auth check (where required) + delegate to `src/lib/db`:

- `GET /api/deal/current` — today's deal, unauthenticated.
- `POST /api/completion` — records a completed game + updates streak; requires session.
- `GET /api/user/stats` — played count, avg time, current/max streak; requires session. Also self-heals a stale streak (resets `curr` to 0 if the user's last completed deal is more than one deal behind today).
- `POST /api/user/share` — completion-time percentile vs. other players of today's deal; no auth required.

### Overlay-driven UI (`src/hooks/overlay.ts`, `src/components/ui`)

Modals (login/stats/help) are not React state — they're driven by the `?overlay=` and `?error=` URL query params (`useOverlayQuery`/`useOverlayRouter`), making them deep-linkable. `Overlay.tsx` is the shell that reads this state.

## Notable non-default config

- `next.config.mjs`: `reactStrictMode: false` — disabled because Phaser's imperative DOM/canvas management doesn't tolerate React's double-invoked effects.
- `tsconfig.json`: path alias `@/*` → `src/*`.
